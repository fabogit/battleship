# Client

Architecture of the Angular client, `packages/client`.

## Reactive model

- `provideZonelessChangeDetection()`, all components `OnPush`, state in Signals. Both are Angular 22 defaults (no `zone.js` dependency; components omit `changeDetection`); the provider is still listed explicitly in `app.config.ts`.
- Services use Angular 22's `@Service()` decorator (root-provided). The server URL is the `SERVER_URL` injection token, so tests can override it.
- **Services:**
  - `ServerWakeService` — cold-start polling ([Cold-start handling](#cold-start-handling)), forced again after a server restart, and the server's start time for a refused seat ([Connection states](#connection-states)).
  - `SessionStore` — credential persistence ([Sessions & reconnection](server.md#sessions--reconnection), [ADR-0069](adr/0069-session-storage-layout.md)): each room's credentials in `localStorage`, the tab's current room in `sessionStorage`; the only module touching either for sessions ([Routes & lobby flow](#routes--lobby-flow)).
  - `RoomEntryService` — `CREATE_ROOM` and `JOIN_ROOM`: stores the credentials of an accepted command in `SessionStore` and returns the room id or the error; `reopen` takes back the stored seat of a room opened in a new tab; `leave` sends `LEAVE_ROOM` before the match and forgets the seat ([Routes & lobby flow](#routes--lobby-flow)).
  - `GameSocketService` — Socket.io lifecycle, connection-status signals (status, close reason, last retry error), typed emit-with-ack helper and server-event listeners ([Socket service](#socket-service)).
  - `GameStateService` — a read-only `snapshot` signal (`PlayerStateSnapshot | null`, `null` until the first `STATE`) plus `computed` views, and local countdown signals re-synced from snapshots ([Game state](#game-state)).
  - `I18nService` — lands with #37: `locale` signal (`it` | `en`), default from `navigator.language`, persisted in `localStorage`. Typed dictionaries where a missing key is a compile error. Until then every screen reads its English words from its own typed object ([Routes & lobby flow](#routes--lobby-flow)).

### Socket service

- The socket is created with the service, idle (`autoConnect: false`): services can listen to server events before the server is awake, and `connect()` opens it once `ServerWakeService` reports the server up. `connect()` does nothing while the socket is connected or retrying, and reopens one that Socket.io gave up on.
- Transports: WebSocket first, then polling (`tryAllTransports: true`), so networks that block WebSocket still connect.
- Handshake: `auth` is a callback, called again on every connection attempt, that sends `{ protocolVersion: PROTOCOL_VERSION }`; the server refuses a client without it ([Protocol: Handshake](protocol.md#handshake), [ADR-0061](adr/0061-handshake-checks.md)). It adds `session`, the current room's credentials from `SessionStore`, when the tab is in a room, and leaves the field out otherwise (`null` is refused); a valid session binds the socket to its seat and brings a `STATE` at once ([ADR-0063](adr/0063-session-rebinding.md)).
- Refusals ([ADR-0070](adr/0070-client-handshake-refusals.md)): a `connect_error` carries the error code as its message. On `SESSION_INVALID` the service drops the credentials it sent (`SessionStore.refuse`, which remembers when the seat was taken) and connects again at once without them; the room page then explains the refused seat ([Connection states](#connection-states)). `PROTOCOL_MISMATCH`, and `SESSION_REPLACED` or `SERVER_SHUTDOWN` followed by the server's disconnect, leave the status at `disconnected` with their close reason.
- `reconnect()` closes an open or opening socket and opens it again, so the handshake sends the current session anew; it leaves a closed socket alone. `RoomEntryService` calls it after a `CREATE_ROOM` or `JOIN_ROOM` that ends in `NO_ACK`, because the server may have moved the socket to a room the client does not know (#52 F1), and when a new tab enters a stored room.
- `status` is one of `CONNECTION_STATUSES`: `disconnected` | `connecting` | `connected`. A drop or a `connect_error` while Socket.io keeps retrying stays `connecting`, a handshake refused by the origin check included. Only a socket that gave up is `disconnected`: closed by the client, disconnected by the server, or refused by a middleware error such as `PROTOCOL_MISMATCH`.
- Beside it ([ADR-0075](adr/0075-client-connection-states.md)): `closeReason`, one of `CLOSE_REASONS` (`protocol-mismatch`, `session-replaced`, `server-shutdown`, `refused`, `server-disconnect`), why the server ended or refused the last connection, set as soon as the server says so and cleared by `connect()` and the next handshake; `retryError`, the last `connect_error` message while Socket.io retries (`xhr poll error`, `websocket error`, …), cleared once connected; `isReconnecting`, whether the attempt in progress follows the drop of an open connection.
- `emitWithAck(event, payload)` accepts only the commands of `ClientToServerEvents`, each with its own payload type. It resolves with the command's `AckResponse`, or with `{ ok: false, error: TransportError }` (one of `TRANSPORT_ERRORS`) when the server did not reply. It never rejects and never queues a command while disconnected ([ADR-0035](adr/0035-command-acks.md)):
  - `NOT_CONNECTED`: the socket was not connected, so nothing was sent.
  - `NO_ACK`: no reply within `ACK_TIMEOUT_MS` (5 s), or the connection dropped first. The server may or may not have applied the command; the next `STATE` tells.
- `on(event, listener)` listens to a server event and returns the function that removes the listener; listeners survive reconnections.

### Game state

`GameStateService` listens to `STATE` and keeps the latest snapshot; `clear()` forgets it (e.g. after leaving the room). `opponentReturned` and `opponentDeparted` compare each `STATE` with the previous snapshot of the same room as it arrives, so no change is missed between two renders ([ADR-0077](adr/0077-opponent-presence-banner.md)). Views:

| View                     | Value                                                                                                                                                                                                  |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `phase`                  | The room's phase; `null` without a snapshot                                                                                                                                                            |
| `isMyTurn`               | `IN_PROGRESS` and `currentTurn` is the receiver's seat, dice animation and pause included                                                                                                              |
| `myFleet`                | `{ ships, shots }`: the fleet without shots in `PLACEMENT`, the fleet and the incoming shots in `IN_PROGRESS` and in `GAME_OVER`; `null` otherwise                                                     |
| `trackingBoard`          | `{ ships, shots, draftTargets }`: in `IN_PROGRESS` the outgoing shots, the ships they sank and the turn's draft; in `GAME_OVER` the revealed opponent fleet under the outgoing shots; `null` otherwise |
| `canPause` / `canResume` | `IN_PROGRESS` with the opponent disconnected, and the match running / paused: when `SET_PAUSED` is accepted                                                                                            |
| `opponentReturned`       | The opponent's nickname for one snapshot after their seat got a socket back; `null` otherwise                                                                                                          |
| `opponentDeparted`       | The nickname of a player whose seat was freed before the match while the client followed the room, until someone takes the seat; `null` otherwise                                                      |
| `hasWon`                 | `null` until `GAME_OVER`; `false` for a match without a winner                                                                                                                                         |

**Game-over boards** ([ADR-0064](adr/0064-game-over-snapshot-boards.md), superseding [ADR-0058](adr/0058-game-over-boards.md)): every board comes from the latest snapshot. At game over it carries both final boards (`myShips`, `incomingShots`, `outgoingShots`, next to `opponentShips`), the shot that ended the match included, so a client that reaches game over without having seen the battle, after a reload for instance, draws the same boards. The service listens to `STATE` only.

Countdowns are in ms, `null` when the snapshot does not carry them ([ADR-0036](adr/0036-countdown-resync.md)):

| Countdown                    | Snapshot field                                              | Frozen while                    |
| ---------------------------- | ----------------------------------------------------------- | ------------------------------- |
| `turnRemainingMs`            | `battle.turnRemainingMs` (`null` during the dice animation) | `battle.isPaused`               |
| `placementRemainingMs`       | `placement.remainingMs`                                     | —                               |
| `startCountdownMs`           | `placement.startCountdownMs`                                | —                               |
| `opponentForfeitRemainingMs` | `opponent.forfeitRemainingMs`                               | — (it runs regardless of pause) |

Each one is the value sent minus the time elapsed since the snapshot arrived (`performance.now()`), never below zero, and every snapshot re-syncs all of them. They tick every `COUNTDOWN_TICK_MS` (250 ms) while one is running, and stop when the longest reaches zero.

## Board & interaction

- The board is a CSS Grid of `<button>` cells rendered with `@for`. 2 × 100 cells is negligible for Signals + OnPush, and buttons give keyboard and screen-reader access for free.
- **Board grid** (`BoardGrid`, `shared/board-grid`): draws one board from its inputs and reports activated cells. It does not read `GameStateService` or the phase, so the same component serves placement, "My fleet" and "Enemy waters".
  - Inputs: `label` (the board's accessible name), `ships`, `shots`, `draftTargets`, `invalidPreview`, `selectedCells` (the selected ship during placement) and `isInteractive` (default `true`). `myFleet` and `trackingBoard` ([Game state](#game-state)) map onto them as they are.
  - Output: `cellActivate`, the `Coordinate` clicked or activated with Enter / Space. A board that is not interactive emits nothing; its cells stay focusable, so it can still be read cell by cell, and report `aria-disabled`.
  - Cell states (`CELL_STATES`, rendered as the button's `data-state`, which the styles select on): `empty`, `ship`, `miss`, `hit`, `sunk`. Every cell of a sunk ship is `sunk`: a cell is sunk when its shot is `SUNK` or when every cell of the ship drawn there was hit. Draft target, invalid preview and selected ship are overlays on a state; the invalid preview draws over the selected ship. Colour is never the only cue: a miss is a dot, a hit a cross, a sunk cell a cross in a frame, and a ship a solid fill much darker (light mode) or lighter (dark mode) than the water; a draft target is a thick frame around a ring, an invalid preview a frame with stripes, the selected ship a double frame.
- **Cell names** ([ADR-0040](adr/0040-cell-names.md)): rows are letters `A`–`J` from the top, columns numbers `1`–`10` from the left, so `B7` is `{ x: 6, y: 1 }`. Both axes are drawn around the board and hidden from assistive technologies, since every cell carries its name.
- **Accessible labels:** the cell name, then its state and overlays, comma-separated: "A2", "B7, hit", "F5, ship, invalid position", "J10, target", "C3, ship, selected". An untouched cell has no state word, so a cell of "Enemy waters" never claims to be empty. The words live in one typed object, `BOARD_GRID_TEXT`, for `I18nService` to provide per locale.
- **Keyboard** ([ADR-0041](adr/0041-board-keyboard-navigation.md)): each board is an ARIA `grid` with a single tab stop (roving `tabindex`): the cell last focused or clicked, `A1` at first.

  | Key                      | Moves focus to                                                     |
  | ------------------------ | ------------------------------------------------------------------ |
  | Arrows                   | The next cell in that direction; nowhere at the edge (no wrapping) |
  | Home / End               | The first / last cell of the row                                   |
  | Ctrl (or ⌘) + Home / End | `A1` / `J10`                                                       |
  | Page Up / Page Down      | The top / bottom cell of the column                                |
  | Enter / Space            | — (activates the cell, as any button)                              |

  Other keys, and arrows with a modifier, keep their browser behaviour.

- **Cell size** ([ADR-0042](adr/0042-board-cell-size.md)): cells share the board's width, between 1.5 rem (24 px, WCAG 2.5.8) and 3 rem (48 px), and reach 2.75 rem (44 px) when the board is about 29 rem (466 px) wide. Phones in portrait get cells of about 1.9–2.3 rem (30–37 px) on 360–430 px viewports with 1 rem (16 px) gutters; at the browser's default font size the page never scrolls sideways. A larger default font size grows the rem, and the board with it: at 24 px ("Very large") the board needs about 423 px, so it scrolls sideways on narrower viewports, most phones in portrait included. Browser zoom does not cause this. Tracked in #39; whether a phone's text-size setting changes the rem is checked on real devices in #38.
- **Placement (touch-first)** (`Placement`, `features/placement`; [ADR-0053](adr/0053-placement-taps.md)): the `PLACEMENT` view. From the top: "Place your fleet", the deadline ("Time left: 0:45", from `placementRemainingMs`) and the opponent's status, the dock, the board ("My fleet"), a live region saying what the last action did, the actions on the selected ship, then "Randomize" and "Confirm fleet" / "Unlock fleet". No drag and drop; drag and drop may come later as a desktop extra.
  - **Dock:** one button per ship, largest first, with its name, one block per cell and a ✓ once it is on the board (read as "Carrier, 5 cells, placed"); `aria-pressed` marks the selected ship. Tapping a ship selects it, and tapping the selected ship again clears the selection.
  - **Tap a cell:** a cell of another placed ship selects that ship; any other cell puts the selected ship there, with the tapped cell as its start (the bow; it extends right or down). A start too close to the right or bottom edge is moved back just enough to fit, so "Carrier" tapped on `J10` lands on `J6`–`J10`. With no ship selected, the view says "Pick a ship from the list first."
  - **Selected ship:** it stays selected after it lands, drawn with the double ring, and the next tap moves it. "Rotate" turns a placed ship about its start (fitted the same way), or switches the direction a dock ship will be placed in; "Remove" puts a placed ship back in the dock, still selected.
  - **Live validity:** every move and rotation is checked with core's `validateDraft` before anything is sent. A refused position keeps the draft as it was, shows the cells it would take as the invalid preview and says why, e.g. "The destroyer cannot go there. Ships may not touch, not even at the corners." "Confirm fleet" stays focusable but inactive (`aria-disabled`) until `validateFleet` accepts the draft, with the reason under it ("Place all five ships to confirm your fleet.").
  - **Randomize** replaces the whole draft with core's `generateRandomFleet(rules, createCryptoRng())` ([ADR-0007](adr/0007-random-placement.md)); the player can still move every ship.
  - **Sync** ([ADR-0054](adr/0054-placement-draft-sync.md)): `PlacementStore`, provided by the view, keeps the draft the view draws, through `createSyncedDraft` (`app/core/synced-draft.ts`), the sync both drafts share. Every change shows at once and sends the whole draft with `UPDATE_PLACEMENT`, as `{ type, start, orientation }` only (the guard refuses the derived coordinates). A `STATE` replaces the draft only while no update waits for its ack; a failed update shows its message ("Not connected to the server. Your last change was not saved.") and, once no other update waits, puts back the server's draft and empties the live region, which described the change just dropped. It empties it only while it still holds that change's feedback: a refused tap or a dock selection made while the update waited stays.
  - **Lock:** "Confirm fleet" sends `CONFIRM_PLACEMENT`; while it runs, and once the snapshot says the fleet is confirmed, the dock, the board (`aria-disabled`) and "Randomize" are inactive, "Your fleet is locked. Unlock it to make changes." shows, and the button becomes "Unlock fleet" (`UNLOCK_PLACEMENT`). The opponent's status reads "Grace is still placing their fleet." or "Grace is ready." in a polite live region, and "Both fleets are ready. The match starts in 3 s." while `startCountdownMs` runs (#28). Until then the second confirmation starts the match at once ([Server: Placement](server.md#placement)).
  - **Keyboard:** dock, actions and cells are buttons, so Tab to a ship, Enter, Tab to the board, arrows, Enter places it; Tab then reaches "Rotate" and "Remove".
- **Battle (touch-first)** (`Battle`, `features/battle`; [ADR-0056](adr/0056-target-draft.md)): the `IN_PROGRESS` view, which turns into the game-over screen. From the top: the turn heading ("Your turn" / "Grace's turn") with what to do in a polite live region ("Pick a target in Enemy waters, then fire." / "Wait for Grace to fire."), the turn deadline when the snapshot has one ("Time left: 0:25", from `turnRemainingMs`; `null` until #30, and nothing depends on it), the board toggle ([Layout](#layout)), "My fleet" (not interactive), "Enemy waters" with "Fire" and its hint, a live region saying what the last tap or shot did, and the error line.
  - **Aim:** during the player's turn a tap on "Enemy waters" toggles a target. With one shot allowed (standard mode; salvo is #32) a tap elsewhere moves the target there; a target tapped again is taken out; a cell already shot is refused ("B7 has already been shot. Pick another cell."), checked with core's `validateTargets`, and nothing is sent. The hint under "Fire" names the target ("Target: B7.").
  - **Fire:** "Fire" stays focusable but inactive (`aria-disabled`) until the draft holds `shotsAllowed` targets, then sends `FIRE { targets }`; while it runs it reads "Firing…" and the board is inactive. During the opponent's turn "Enemy waters" is inactive and the hint says "You can aim once it is your turn."
  - **Sync:** `BattleStore`, provided by the view, keeps the turn's draft with the same `createSyncedDraft` as `PlacementStore` keeps the fleet ([ADR-0054](adr/0054-placement-draft-sync.md)): every change shows at once and sends the whole draft with `UPDATE_TARGETS`; a `STATE` replaces it only while no update waits for its ack; a failed update shows its message ("Not connected to the server. Your last move was not saved.") and, once no other update waits, puts back the server's draft and empties the live region, unless a refused tap made while the update waited has replaced its feedback. Outside the player's turn the draft is empty.
  - **Shots:** every `SHOT_RESOLVED` is announced in the live region, by either player: "You fired at B7: miss.", "You fired at C7 and sank Grace's destroyer!", "Grace fired at A1: hit.", "Grace fired at F8 and sank your carrier."
  - **Game over:** the heading says "You won!", "You lost" or, without a winner, "Match abandoned"; the reason follows ("You sank Grace's whole fleet.", "Grace surrendered.", …, one sentence per `GameOverReason`), then "Enemy waters now shows Grace's whole fleet, the ships you did not find included." and a "New match" link home. Both boards stay, drawn from the game-over snapshot ([Game state](#game-state)), with the board toggle, and neither is interactive. Surrender, rematch and leaving are not offered until their room logic lands (#35, #36; [ADR-0046](adr/0046-commands-ahead-of-room-logic.md)).
  - **Keyboard:** Tab to "Enemy waters", arrows to a cell, Enter aims; Tab reaches "Fire", Enter fires. Shift+Tab goes back to the board on the cell last used.

## Routes & lobby flow

Two routes, both under the app shell, which shows the app name (a link home) and the server status above every page ([ADR-0049](adr/0049-room-route.md)); after `PROTOCOL_MISMATCH` or `SESSION_REPLACED` a connection screen replaces the page ([Connection states](#connection-states)):

| Route        | Page   | Shows                                                                      |
| ------------ | ------ | -------------------------------------------------------------------------- |
| `/`          | `Home` | Nickname and "Create room"                                                 |
| `/r/:roomId` | `Room` | The room for both players: join form, waiting screen, then the match views |

Any other address redirects to `/`. The room id reaches `Room` as an input (`withComponentInputBinding()`).

- **Server status** (`ServerStatus`, `shared/server-status`): started by the shell, it runs the wake-up poll, then opens the socket ([Cold-start handling](#cold-start-handling)), and shows "Waking up the server…" (with the "about half a minute" hint), "The server is not responding" with a retry button, "Connecting…", "Connected", and the states of [Connection states](#connection-states): reconnecting, retrying, restarting and refused. The line is an `aria-live` region.
- **Nickname** (`NicknameForm`, `shared/nickname-form`): one labelled field and one submit button, shared by the home and join screens and built with Signal Forms ([ADR-0051](adr/0051-signal-forms.md)). It validates with core's `parseNickname` (trimmed, 1 to `NICKNAME_MAX_LENGTH` UTF-16 code units, the characters of [ADR-0060](adr/0060-nickname-characters.md)) and carries `maxlength`, so it accepts exactly what the server's guard accepts and hands over the trimmed nickname. An error shows after a submit, with `aria-invalid` on the field: "Enter a nickname." for an empty or blank field, "Use letters, numbers, punctuation or emoji. Invisible and control characters are not allowed." for a refused character.
- **Before the connection** ([ADR-0050](adr/0050-entry-before-connection.md)): the field is usable while the server wakes up. The submit button stays focusable but inactive (`aria-disabled`) until the socket is connected, with the hint "Available once the server is connected"; a submit then does nothing, so a command is never queued. While the command runs, the button reads "Creating room…" / "Joining room…" and ignores further submits.
- **Create** (`Home`): `CREATE_ROOM { nickname }`, then navigation to `/r/<roomId>`. A refusal stays on the home screen with its message (`SERVER_FULL`: "The server is full right now…"; no reply: "The server did not answer…").
- **Room page** (`Room`): picks one view, in this order:
  1. A room id that fails core's `isRoomId` → "Room not found", without asking the server. A room whose stored seat the server refused with `SESSION_INVALID` since the app started, and that holds no new seat → the refused seat's explanation, even over a snapshot the tab still holds ([Connection states](#connection-states), [ADR-0076](adr/0076-refused-seat-explanation.md)); its join form, where offered, answers `ROOM_NOT_FOUND` with "Room not found" and `ROOM_FULL` with "This room is full".
  2. `SessionStore` holds a seat in this room, but this tab has entered another room since (a later accepted `CREATE_ROOM` or `JOIN_ROOM`, e.g. after the header link or "New match", then Back) → "You left this room", with a "Create a new room" link home. The server moved the socket out of the room ([ADR-0045](adr/0045-socket-seat-binding.md)), so no `STATE` for it would come. The current room lives in `sessionStorage`, so this holds after a reload too ([ADR-0069](adr/0069-session-storage-layout.md)).
  3. The latest snapshot belongs to this room → by phase: `WAITING_FOR_OPPONENT` shows the waiting screen; `PLACEMENT` shows the placement view; `IN_PROGRESS` and `GAME_OVER` show the battle view, which becomes the game-over screen ([Board & interaction](#board--interaction)). `RULES_NEGOTIATION` shows the waiting screen until its rules part lands (#27).
  4. `SessionStore` holds a seat in this room, the tab's current room, but no snapshot has arrived → "Entering the room…". The handshake sends the seat's credentials, and the server answers with the room's `STATE`.
  5. Otherwise the join form: "Join room" sends `JOIN_ROOM { roomId, nickname }`. `ROOM_NOT_FOUND` replaces it with "Room not found", `ROOM_FULL` with "This room is full", both with a "Create a new room" link home; any other failure keeps the form with its message. Opening another room's address forgets the failure.
- **Opponent presence** (`Presence`, `features/presence`): above the waiting screen, placement and battle, kept while the view below changes ([Connection states](#connection-states)).
- **Leave room** ([ADR-0078](adr/0078-leaving-before-the-match.md), [ADR-0080](adr/0080-leave-room-beside-the-heading.md)): on the right of the heading of the waiting screen and placement, which project it, a compact "Leave room", still 2.75 rem (44 px) high, sends `LEAVE_ROOM`. Its hint, "Your seat is freed for someone else, and you go back to the home screen.", is its description only (`aria-describedby` to a `hidden` paragraph), and a failure message spans the row under the heading. It sits above the board, in view without scrolling from 320×568 to 1280×800, presence banner included. While the command runs it reads "Leaving…" and ignores taps. Once accepted, `SessionStore.forget` drops the room's credentials and the tab's current room, `GameStateService` forgets the snapshot, and the page goes home; Back to the room link shows the join form. A refusal stays with its message ("The match has started, so the room can no longer be left." for `NOT_ALLOWED`, the room-entry messages otherwise); `NO_ACK` reconnects, as after `CREATE_ROOM` and `JOIN_ROOM`. It is not offered once the match has started: the server refuses it there until #35 and #36.
- **Waiting screen** (`Lobby`, `features/lobby`): "Waiting for your opponent", the player's nickname and the room link, `/r/<roomId>` as an absolute URL, in a labelled read-only field that selects itself on focus, then "Share link" and "Copy link" ([ADR-0079](adr/0079-share-dialog.md)). The rules part of the lobby comes with #27.
  - "Copy link" writes the link to the clipboard and says "Link copied.", or, without clipboard access, asks to copy the link from the field.
  - On a phone or tablet (`(pointer: coarse)` with the Web Share API), "Share link" opens the system share sheet; closing the sheet is not an error.
  - Elsewhere, "Share link" opens the share dialog "Share the room link", a modal `<dialog>`: the line "Scan the code with a phone to open the room there, or copy the link and send it.", a QR code of the link (`QrCode`, `shared/qr-code`, an SVG image named "QR code of the room link, <link>"), the link in a read-only field, "Copy link" (focused when the dialog opens), "Other apps…" (the system share sheet, only where the browser has the Web Share API) and "Close". Esc closes it too, and focus returns to "Share link". The dialog has its own message line, and the page's stays empty while it is open. On a screen under 45rem (720px) tall, the dialog tightens its spacing and the code shrinks with the height, to no less than 12rem (192px), so "Link copied." stays in view on a screen 568px tall, or 640px with "Other apps…", whose buttons take a second row.
  - A sheet that fails to open opens the dialog instead, with "This browser could not open its share options. Scan the code or copy the link instead.". It counts as failed on any error but `AbortError`, and on an `AbortError` sooner than `NATIVE_SHEET_FAILURE_MS` (500 ms) after the call: desktop Linux Chromium has the API but no sheet, and rejects at once. From then on "Share link" goes straight to the dialog and "Other apps…" is inactive. A failed "Other apps…" shows the same message. A tap while the sheet of an earlier tap is still open is ignored: no second `navigator.share` call is made until the first one settles, since the browser would reject it with `InvalidStateError`.
- **Credentials** ([ADR-0069](adr/0069-session-storage-layout.md)): `RoomEntryService` saves the `{ roomId, playerSecret }` of an accepted `CREATE_ROOM` or `JOIN_ROOM` in `SessionStore`, and their room becomes the tab's current room.
  - Storage: `localStorage` holds one entry per room, `battleship:session:<roomId>` → `{ roomId, playerSecret, expiresAt }`, kept for `SESSION_STORE_TTL_MS` (24 h) after it was saved ([ADR-0013](adr/0013-session-persistence.md)). `sessionStorage` holds the current room under `battleship:current-room`: one per tab, kept across reloads.
  - Both are read once when the app starts, as untrusted input: an entry that is not exactly `{ roomId, playerSecret, expiresAt }`, fails core's `parseSessionCredentials`, sits under another room's key or has expired is removed, and so is a current room that fails `isRoomId`. Storage that throws leaves the store in memory for the tab.
  - Reload: the handshake sends the current room's credentials and the server restores the seat ([Socket service](#socket-service)), whatever the phase; at game over the snapshot carries both final boards.
  - New tab: it starts in no room. Opening `/r/<roomId>` with stored credentials makes that room current (`RoomEntryService.reopen`), reconnecting if the socket is already open, so closing the tab and opening the room link again restores the match. A tab already in another room shows "You left this room" instead.
- **Words:** each screen keeps its strings in one typed object next to it (`HOME_TEXT`, `ROOM_TEXT`, `LOBBY_TEXT`, `PLACEMENT_TEXT`, `BATTLE_TEXT`, `PRESENCE_TEXT`, `NICKNAME_FORM_TEXT`, `BOARD_GRID_TEXT`, `SERVER_STATUS_TEXT`, `CONNECTION_SCREEN_TEXT`, `ROOM_ENTRY_TEXT` for the failure messages), for `I18nService` (#37).

## Connection states

Decisions: [ADR-0075](adr/0075-client-connection-states.md) (status line, screens, restart), [ADR-0076](adr/0076-refused-seat-explanation.md) (refused seat), [ADR-0077](adr/0077-opponent-presence-banner.md) (opponent presence).

- **Status line** (`ServerStatus`), from the wake-up poll, then the socket ([Socket service](#socket-service)):

  | State                                         | Line                                                                                                             | Button      |
  | --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | ----------- |
  | Opening a first connection                    | "Connecting…"                                                                                                    | —           |
  | Retrying after a drop (`isReconnecting`)      | "Connection lost. Reconnecting…", and in a room "Your seat is kept for 3 minutes after you lose the connection." | —           |
  | Either, after a failed attempt (`retryError`) | Adds "The last attempt failed (xhr poll error). Trying again…"                                                   | —           |
  | After `SERVER_SHUTDOWN`                       | "The server is restarting…" / "You are reconnected as soon as it is back."                                       | —           |
  | `PROTOCOL_MISMATCH`                           | "Refused by the server: this page is out of date."                                                               | (screen)    |
  | `SESSION_REPLACED`                            | "Disconnected: this match is open in another tab or on another device."                                          | (screen)    |
  | Another refused handshake                     | "The server refused the connection."                                                                             | "Try again" |
  | Disconnected by the server without a reason   | "Disconnected from the server."                                                                                  | "Try again" |

  "Try again" polls `/health` again (`wake({ isForced: true })`), then connects. A handshake refused by the origin check is retried by Socket.io, so it shows as retrying with its error, not as refused (#51 F9).

- **Restart:** when `SERVER_SHUTDOWN` arrives and the server disconnects the socket, `ServerStatus` polls `/health` again, forced, and connects once the next instance answers (#51 F15). The new instance does not know the room, so the handshake is refused with `SESSION_INVALID` and the room page explains it. On a Render deploy the event does not arrive ([Deployment: Backend](deployment.md#backend-render)): the tab shows "Connection lost. Reconnecting…", Socket.io reaches the new instance on its own, and the same explanation follows.
- **Connection screens** (`ConnectionScreen`, `shared/connection-screen`), shown by the shell instead of the page while the close reason lasts:
  - `PROTOCOL_MISMATCH`: "Please reload the page", "The game was updated while this page was open, and the server no longer accepts this version. Reload the page to get the new one. If this message comes back, wait a minute and reload again.", and "Reload".
  - `SESSION_REPLACED`: "This match is open somewhere else", "You opened this room in another tab or on another device, so the match moved there.", and "Play here" ("Playing here takes the match back, and the other tab or device stops."), which connects again: latest connection wins, so the other tab gets this screen.
- **Refused seat** (the room view `seat-lost`): `classifySeatLoss` compares when the seat was taken (`SessionStore.refusal`) with when the server started (`ServerWakeService.startedAt()`, one `GET /health`: `Date.now()` minus `uptime`), and looks at whether the tab saw the match end:

  | `SEAT_LOSSES` | When                                                                                                  | Heading                          | Offers                         |
  | ------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------- | ------------------------------ |
  | `restarted`   | The server started after the seat was taken                                                           | "The server restarted"           | "Create a new room"            |
  | `closed`      | Otherwise, the room's latest snapshot here was `GAME_OVER`                                            | "This room has closed"           | "Create a new room"            |
  | `given-up`    | Otherwise, the server has run since the seat was taken                                                | "You lost your seat"             | Join form, "Create a new room" |
  | `unknown`     | Otherwise: `/health` did not answer or has not yet, or no stored session said when the seat was taken | "You are no longer in this room" | Join form, "Create a new room" |

  The explanations quote `DISCONNECT_FORFEIT_MS` and `GAME_OVER_TTL_MS` in minutes, e.g. "You were away for more than 3 minutes, or you left the room, so your seat was given up. If the room is still waiting for a player, you can join it again." Joining forgets the refused seat's snapshot of the room first, so the new seat, `P1` when the creator left ([ADR-0073](adr/0073-room-lifecycle-with-forfeits.md)), starts from its own `STATE`.

- **Opponent presence** (`Presence`, above the waiting screen, placement and battle; every sentence but the countdown in one polite live region that the room page keeps across those views):
  - "Grace is disconnected." while `opponent.isConnected` is `false`, game over included. In production the server notices a closed tab about 10 s after it closes (Render's proxy); locally at once.
  - The forfeit countdown, `role="timer"`, from `opponentForfeitRemainingMs`: "Grace loses the match in 2:41 unless they come back." during the match, "Grace's seat is freed in 2:41 unless they come back." before it.
  - During the match: "The match is paused." (`battle.isPaused`) or, while the opponent is away and the match runs, "The match is running."; "Pause match" / "Resume match" when `canPause` / `canResume`, sending `SET_PAUSED` ("Pausing…" / "Resuming…" while it waits, further taps ignored; a refusal in an alert, e.g. "Your opponent is back, so the match goes on." for `NOT_ALLOWED`, cleared once neither control is offered and not shown again when the opponent drops again).
  - "Grace is back." for one snapshot after the return (`opponentReturned`).
  - "Grace left the room, so their seat is free again." after a seat freed before the match, until someone takes it (`opponentDeparted`): the player is back on the waiting screen in their own seat.

## Layout

Decision: [ADR-0057](adr/0057-battle-layout.md).

- **Narrow screens** (below 52 rem, 832 px; phones in both orientations, tablets in portrait): one board at a time, picked with a toggle of two buttons, "My fleet" and "Enemy waters" (`aria-pressed`, `aria-controls`). The toggle follows the turn: "Enemy waters" during the player's turn and at game over, "My fleet" during the opponent's. After every `SHOT_RESOLVED` the board the shot landed on stays in front for `SHOT_HOLD_MS` (1.5 s), so both players see where it fell, then the next turn's board comes forward. A board picked by hand stays until the turn changes. The board's own heading is hidden visually, since the toggle names it; the hidden board is `display: none`.
- **Wide screens** (52 rem and up): both boards side by side, each with its heading, and no toggle. The app shell widens from 40 rem to 68 rem while the battle view is shown (`:host:has(app-battle)`), so each board reaches 3 rem (48 px) cells.
- The breakpoint is a CSS media query in the view's styles; nothing in code reads the viewport.
- Room link shared through the system share sheet on phones and tablets, and through the share dialog (QR code, link, "Copy link") elsewhere; "Copy link" is on the page too ([Routes & lobby flow](#routes--lobby-flow)).

## Cold-start handling

`ServerWakeService` handles the cold start:

1. On app start, `GET /health` until it answers, giving up after 90 s. `wake()` returns at once once the server has answered, unless forced (`{ isForced: true }`), as after `SERVER_SHUTDOWN` and from the retry button ([Connection states](#connection-states)). Each attempt may use all the time left before giving up, since Render holds the request open until the instance is ready (step 2); failed attempts are spaced by an exponential backoff (500 ms doubling, cap 5 s). Giving up shows a retry button.
2. While Render serves its loading page the request fails as a CORS/parse error: treat any non-JSON or failed response as "still waking". _Measured (#8):_ Render held `fetch` requests open until the instance was up rather than serving the loading page. With the original 10 s per-attempt timeout, two attempts were aborted and the third succeeded about 23 s after the page opened (24.4 s to a connected socket, three requests). _Re-measured after the fix (#51):_ one request, held open by Render and answered with 200 after 22.8 s; connected after 23.2 s. The gain (about 1 s) is within noise: the fix removes the aborted requests rather than shortening the wait. The non-JSON handling stays as a fallback. The waking hint says a sleeping server "usually takes about half a minute".
3. UI shows a "Waking up the server…" state; nickname entry stays usable meanwhile ([Routes & lobby flow](#routes--lobby-flow)).
4. The Socket.io connection is opened only after `/health` succeeds.

_A refused origin looks like a cold start (#51):_ `/health` answers a foreign origin with a 403 without CORS headers ([D21](adr/0021-origin-policy.md)), which the browser cannot tell apart from Render's loading page, so the page shows "Waking up the server…" for 90 s and then "The server is not responding". A Socket.io handshake refused by `allowRequest` likewise keeps the socket active and retrying; only a middleware error (`next(err)`, the handshake check's `PROTOCOL_MISMATCH`/`SESSION_INVALID`, [ADR-0061](adr/0061-handshake-checks.md)) stops it. The status line shows a retried handshake with its last error ("The last attempt failed (xhr poll error). Trying again…") and a refused one with its reason ([Connection states](#connection-states)). A foreign origin never gets that far: its `/health` poll already fails like a sleeping server's. Telling the two apart needs the server to answer a foreign origin in a way the browser lets the page read (CORS headers on the 403), a server change left out of #25 and tracked in #114.
